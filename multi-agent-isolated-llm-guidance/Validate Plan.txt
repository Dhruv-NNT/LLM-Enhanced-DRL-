Yes. Your choices mean this:

```text
1. Joint LLM swap
→ evaluate the LLM guidance as a whole group decision, not one aircraft at a time.

2. Every decision
→ whenever the controller says an aircraft is guidance-eligible, call the LLM live.

3. Isolated per run
→ each experiment gets its own separate memory file, so memory from one run does not leak into another run.
```

This is a **strong but slower** setup. It is more realistic for multi-agent behavior, but credit assignment becomes harder because if the joint LLM rollout is better, we may not know exactly which aircraft’s LLM action caused the improvement.

# Training Flow for: Joint LLM Swap + Every Decision + Isolated Memory

## 1. At the start of each experiment

Create a separate memory file for that run.

Example:

```text
memory/run_seed42_llm_guided_joint_swap/decision_memory.json
memory/run_seed43_llm_guided_joint_swap/decision_memory.json
```

Do **not** share memory across experiments.

This is important because the memory system can retrieve past decisions and insert them into later LLM prompts. If all experiments share one memory file, later experiments may benefit from earlier experiments, which weakens fairness. The memory system is only meant to provide small hints, and the current simulator preview should still override memory. 

---

## 2. At every simulator step

First, the MAPPO actor produces actions for all active aircraft.

For each active aircraft:

```text
obs_i → MAPPO actor → action distribution π(a | obs_i)
```

Then MAPPO samples or selects:

```text
a_MAPPO_i
```

So we get a MAPPO action dictionary:

```text
A_MAPPO = {
  A1: a_MAPPO_1,
  A2: a_MAPPO_2,
  ...
}
```

This is the action dictionary used in the **real training episode**.

---

## 3. Call the LLM at every eligible guidance decision

Because you chose **Every Decision**, the training loop should call the LLM whenever the existing controller finds guidance-eligible aircraft.

This does **not** necessarily mean every aircraft at every step.

It means:

```text
If the controller says an entered aircraft needs guidance,
call the LLM.
```

The existing controller already decides which aircraft are actionable using call types such as:

```text
EXECUTE_TURN
EMERGENCY_MANEUVER
MERGE_BACK
```

It also sorts actionable aircraft by urgency, such as earliest predicted bad event and smaller predicted minimum separation. 

The LLM returns validated heading-change actions for all listed aircraft. The controller already validates and guardrails the LLM output before passing it forward. 

So we get:

```text
A_LLM = {
  A1: a_LLM_1,
  A3: a_LLM_3,
  ...
}
```

Only aircraft included in the LLM prompt appear in `A_LLM`.

---

## 4. Memory is retrieved only from this run’s isolated memory file

Before the LLM prompt is built, the memory system may retrieve similar older cases from the same experiment’s memory file.

Memory may return something like:

```text
A1 remembered action = -15°
```

or corrected memory:

```text
A1 corrected action = -25°
```

So we form:

```text
A_MEMORY = {
  A1: a_MEMORY_1,
  A3: a_MEMORY_3,
  ...
}
```

But memory remains advisory. It is not the MAPPO policy, not a planner, and not a replacement for simulator preview safety. The memory README explicitly says the current preview remains the source of truth. 

---

## 5. Real training branch: execute MAPPO action

This is very important.

Even though we called the LLM, the **real environment step** should execute MAPPO’s action:

```text
real_env.step(A_MAPPO)
```

So the real training trajectory is still generated by MAPPO.

This keeps PPO/MAPPO valid.

The real transition stores:

```text
obs
global_state
MAPPO action
MAPPO log probability
value estimate
reward
done
LLM action label, if available
memory action, if available
```

---

# 6. Shadow rollout comparison

Before stepping the real environment, clone the simulator state.

You will run three shadow branches from the same pre-step state.

## Branch 1: MAPPO shadow

Use MAPPO actions for all active aircraft:

```text
A_shadow_MAPPO = A_MAPPO
```

Then simulate for `H` steps.

Recommended:

```text
H = 5
```

After the first step, continue with deterministic MAPPO actions for the rest of the shadow horizon.

So:

```text
Step 1: use A_MAPPO
Step 2 to H: use deterministic MAPPO actions
```

Compute discounted return:

```text
G_MAPPO = r_t + γ r_t+1 + γ² r_t+2 + ... + γ^(H-1) r_t+H-1
```

---

## Branch 2: Joint LLM shadow

This is your selected option.

For all LLM-guided aircraft, replace their first action with the LLM action.

For aircraft not guided by the LLM, keep MAPPO action.

Example:

```text
A_MAPPO = {
  A1: +5,
  A2: 0,
  A3: -10,
  A4: +15
}

A_LLM = {
  A1: +15,
  A3: -25
}
```

Then:

```text
A_shadow_LLM = {
  A1: +15,   # replaced by LLM
  A2: 0,     # kept MAPPO
  A3: -25,   # replaced by LLM
  A4: +15    # kept MAPPO
}
```

Then simulate for `H` steps.

```text
Step 1: use joint LLM-swapped action dictionary
Step 2 to H: use deterministic MAPPO actions
```

Compute:

```text
G_LLM = r_t + γ r_t+1 + γ² r_t+2 + ... + γ^(H-1) r_t+H-1
```

This tests:

> If all guided aircraft followed the LLM suggestion together, would the short-term outcome be better than MAPPO?

---

## Branch 3: Joint memory shadow

If memory actions exist, create a memory branch.

For aircraft with retrieved memory action, use memory action.

For aircraft without memory action, keep MAPPO action.

Example:

```text
A_MEMORY = {
  A1: -15
}
```

Then:

```text
A_shadow_MEMORY = {
  A1: -15,   # memory action
  A2: 0,     # MAPPO
  A3: -10,   # MAPPO because no memory
  A4: +15    # MAPPO
}
```

Then simulate for `H` steps and compute:

```text
G_MEMORY = r_t + γ r_t+1 + γ² r_t+2 + ... + γ^(H-1) r_t+H-1
```

---

# 7. How to use the joint shadow returns

Now compare:

```text
G_MAPPO
G_LLM
G_MEMORY
```

Because this is **joint LLM swap**, the LLM return is a group-level result.

So if:

```text
G_LLM > G_MAPPO
```

it means:

> The joint LLM-guided action set performed better than the MAPPO action set over the short shadow horizon.

Then use this to weight the LLM imitation loss.

---

## LLM imitation loss

For every aircraft that received an LLM label:

```text
L_LLM_i = -log π_MAPPO(a_LLM_i | obs_i)
```

Weight it using the joint improvement:

```text
w_joint = max(0, G_LLM - G_MAPPO)
```

Then:

```text
L_LLM_total = w_joint × Σ_i phase_weight_i × L_LLM_i
```

In simple words:

> If the joint LLM rollout is better than the MAPPO rollout, train MAPPO more strongly toward the LLM actions. If the joint LLM rollout is not better, do not strongly imitate it.

The total MAPPO update becomes:

```text
L_total =
L_PPO_actor
+ c_v L_value
- c_e Entropy
+ λ_LLM L_LLM_total
```

The PPO part still uses the real MAPPO-executed actions.

The LLM part uses the LLM actions only as teacher labels.

---

# 8. Important consequence of joint LLM swap

Joint LLM swap gives a realistic multi-agent comparison, but it has weaker credit assignment.

Example:

```text
A1 LLM action is very good.
A3 LLM action is bad.
Together, G_LLM is still better than G_MAPPO.
```

In that case, both A1 and A3 get some imitation credit, even though A3 may not deserve it.

So this option is more realistic but less precise.

That is the main trade-off.

---

# 9. Memory correction logic under joint swap

Memory correction is harder with joint swap.

If:

```text
G_MEMORY < G_MAPPO
```

or:

```text
G_MEMORY < G_LLM
```

we know the memory branch was worse.

But if multiple memory actions were used together, we may not know which memory action caused the bad result.

So use this safe rule:

## Case A: only one memory action was used

If only one aircraft had a memory action, then correction is safe.

If:

```text
G_MEMORY < max(G_MAPPO, G_LLM) - margin
```

then update that memory case:

```json
"result.corrected": best_action_for_that_aircraft,
"result.note": "shadow rollout return was lower than MAPPO/LLM alternative"
```

The memory README already has reserved fields for `result.corrected` and `result.note`, but automatic update is not currently implemented. 

---

## Case B: multiple memory actions were used

If multiple memory actions were used together, do **not blindly update all of them**.

Instead, do one of these:

### Safer option

Log the memory branch as underperforming, but do not update individual memory cases.

### Better but slower option

Run an extra per-memory attribution check.

For each memory-guided aircraft:

```text
Swap only that aircraft’s memory action.
Keep others on MAPPO action.
Run short shadow rollout.
Check whether that individual memory action was bad.
```

Then update only the memory case that individually underperformed.

Since you said slower training is acceptable, I recommend the better but slower option.

---

# 10. Final step update order

At the end of each episode, update MAPPO normally.

Use:

```text
1. PPO actor loss from real MAPPO actions
2. Critic value loss from real trajectory returns
3. Entropy bonus
4. Return-weighted LLM imitation loss from joint LLM shadow comparison
```

So the update is:

```text
L_total =
L_PPO_actor
+ c_v L_value
- c_e Entropy
+ λ_LLM × w_joint × Σ_i phase_weight_i[-log π(a_LLM_i | obs_i)]
```

Where:

```text
w_joint = max(0, G_LLM - G_MAPPO)
```

possibly clipped or normalized.

# Final interpretation

Choosing **Joint LLM swap + Every decision + Isolated per run** means you are testing a fairly strong version of LLM-guided MAPPO:

```text
The LLM is called at every guidance opportunity.
The LLM’s multi-aircraft action set is evaluated jointly.
The real policy still remains MAPPO-driven.
The memory file is kept isolated for fair comparison.
```

This setup is slower, but it gives a realistic test of whether the LLM’s joint guidance helps the multi-agent system. The main weakness is that joint swap makes it harder to know which individual aircraft action caused improvement, so memory correction should be done carefully, preferably with an extra per-memory attribution rollout before updating individual memory cases.
